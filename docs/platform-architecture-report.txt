CANTEEN/CAFE MANAGEMENT SAAS - ARCHITECTURE AND LAUNCH REPORT
================================================================

Document purpose:
- Summarize the planned transition from demo application to production-ready SaaS.
- Cover business model, legal/trust concerns, Supabase structure, tech stack, project structure, phases, and challenges.
- Keep the document text-first so it can be shared, reviewed, or converted into formal docs later.

Current project status:
- Current app type: Next.js App Router application in active development.
- Hosting target: Vercel.
- Current data mode: Supabase-backed vendor, menu, order, stock, and ledger data.
- Current routing: vendor-scoped dashboard routes under /app/[vendorSlug].
- Current backend: Next.js server actions and Supabase query helpers.
- Current database: Supabase PostgreSQL with RLS and Realtime configuration.
- Current auth: temporary presentation cookie; Supabase Auth memberships are required
  before production onboarding.
- Current target: production SaaS for local canteen/cafe vendors, starting in Pune.

Short glossary:
- B2B: business-to-business.
- SaaS: subscription software delivered online.
- PWA: installable web app that can behave like a mobile app.
- RLS: Row Level Security; database-level access rules.
- SSR: server-side rendering/session handling before page output.
- API route: backend endpoint inside the NextJS app.
- Tenant: one vendor workspace/account.
- vendor_id: database key that separates one vendor's data from another.
- vendor_members: table that maps users to vendor roles.
- Realtime: live updates without manual refresh.
- WebP: efficient image format for web/mobile.


1. BUSINESS MODEL
=================

Business model:
- B2B subscription SaaS.
- Vendors pay subscription fees for software access.
- No ads.
- No hidden monetization.
- No customer payment handling in the first launch phase.
- No food marketplace positioning.
- No lending/credit/financial-product positioning.

Recommended positioning:
- "Canteen/cafe management software for local vendors."

Avoid positioning as:
- Food delivery platform.
- Payment platform.
- Marketplace.
- Credit or lending app.
- Data monetization platform.

Initial market:
- Pune local vendors.
- Start with a small private pilot.
- Focus on vendors who can use a phone-first PWA.

Play Store strategy:
- Do not publish to Play Store as the first milestone.
- Start as a web/PWA app.
- Add Capacitor and Play Store distribution after real usage is proven.
- Reason: Play Store has cost, verification, review, privacy disclosure, and account deletion requirements.

Hosting strategy:
- Host the NextJS app on Vercel.
- Reason: Vercel is the native deployment platform for NextJS and keeps early deployment friction low.


2. PRODUCT PRINCIPLES
=====================

Core principles:
- Mobile-first.
- Simple onboarding.
- Vendor operations should be abstract and easy.
- Staff should only see dashboards relevant to their role.
- Vendor data must be isolated.
- Legal and privacy promises must match the actual system.
- No feature should require manual technical work by vendors.

Image handling principle:
- Vendor selects image.
- App previews it.
- Backend validates and normalizes it.
- Sharp converts/resizes/compresses it.
- Supabase Storage stores the optimized image.
- Vendor never manually compresses, resizes, crops, or converts files.

Security principle:
- Frontend checks are for user experience.
- Backend validation is mandatory.
- Supabase RLS is the final data access enforcement layer.


3. CORE USER TYPES
==================

Platform owner:

Vendor owner:

Customer:

4. TENANT MODEL
===============

Primary tenant key:
- vendor_id

Meaning:
- vendor_id is the tenant/workspace/root business boundary.
- It is the top-level ownership key for business data.

Do not use as tenant key:
- vendor_membership_id

Reason:
- Membership represents one user's relationship with one vendor.
- It is for roles and access control.
- It should not define ownership of business rows like orders or menu items.

Mental model:
- vendors = root folders.
- vendor_members = access control list.
- business tables = files inside the vendor workspace.
- RLS = filesystem permission checker.

URL slug:
- vendorSlug is useful for routes.
- vendorSlug is not trusted for security.
- RLS must use vendor_id and auth.uid().

9. STORAGE STRUCTURE
====================

Storage purpose:
- Store optimized images.
- Do not store images directly in PostgreSQL.
- PostgreSQL stores metadata and references.

Recommended table:
- media_assets

media_assets columns:
- id
- vendor_id
- bucket
- path
- kind
- mime_type
- width
- height
- size_bytes
- created_by
- created_at
- deleted_at

Recommended buckets:
- vendor-public-assets
- vendor-private-assets

Public assets:
- vendor logo
- food/menu item images

Private assets:
- employee avatars
- internal documents later

Recommended storage paths:
- vendors/{vendor_id}/logos/{asset_id}.webp
- vendors/{vendor_id}/menu-items/{menu_item_id}/{asset_id}.webp
- vendors/{vendor_id}/members/{member_id}/{asset_id}.webp

Recommended references:
- vendors.logo_asset_id -> media_assets.id
- menu_items.image_asset_id -> media_assets.id
- vendor_members.avatar_asset_id -> media_assets.id

Why avatar_asset_id belongs on vendor_members:
- One user can later belong to multiple vendors.
- Their identity/profile may be shared.
- Their role-specific avatar or staff image can be vendor-specific.


10. IMAGE NORMALIZATION
=======================

Library:
- sharp

Where it runs:
- NextJS server route or server action.
- Never in the browser.

Upload flow:
- Client selects image.
- Client shows preview.
- NextJS API receives file.
- Server verifies session.
- Server verifies vendor membership.
- Server verifies role permission.
- Server validates MIME type and size.
- Sharp resizes/crops/compresses/converts image.
- Server uploads final WebP to Supabase Storage.
- Server inserts media_assets row.
- Server links media_assets row to vendor/menu/member record.

Suggested formats:
- Accept JPG, PNG, WebP.
- Store WebP.

Suggested output rules:
- Vendor logo: 512 x 512 WebP, max around 150 KB.
- Employee avatar: 512 x 512 WebP, max around 120 KB.
- Menu item image: 1024 x 768 or square WebP, max around 250 KB.

Vendor experience:
- Vendor should only see "Upload image".
- System handles optimization quietly.


11. RLS SECURITY MODEL
======================

RLS requirement:
- Enable RLS on all exposed tables.

Base policy idea:
- A user can access a row only if an active vendor_members row exists for:
  - vendor_members.user_id = auth.uid()
  - vendor_members.vendor_id = row.vendor_id
  - vendor_members.status = active

Role policy idea:
- Writes depend on role.

Example access by role:
- owner: full access.
- admin: most vendor operations.
- manager: menu, stock, orders, reports.
- cashier: orders and payment confirmation.
- kitchen: order queue and status progression.
- accountant: ledger, expenses, profit/loss.

Important RLS rule:
- Do not rely on frontend route guards for security.
- Route guards improve UX only.
- RLS prevents actual cross-vendor data access.

Testing requirement:
- Test that vendor A cannot read vendor B data.
- Test that vendor A cannot write vendor B data.
- Test each role can only perform allowed actions.
- Test disabled members lose access.
- Test unauthenticated users cannot access staff/vendor tables.

13. REALTIME
============

Realtime use cases:
- Kitchen order updates.
- Queue token display.
- Staff dashboard updates.
- Admin order monitoring.

Initial approach:
- Supabase Realtime Postgres Changes.

Potential scaling concern:
- Per-user RLS checks on realtime changes can become heavier at scale.

Future approach:
- Use server-side broadcast channels if direct Postgres Changes becomes inefficient.

Lifecycle concerns:
- Mobile app resume/pause.
- Network loss.
- Reconnect state.
- Duplicate subscriptions.
- Stale queue display.

22. FINAL SUMMARY
=================

The app should evolve from a demo into a local-first B2B SaaS platform.
The strongest foundation is:

- NextJS for app and server validation.
- Supabase for Auth, PostgreSQL, Storage, and Realtime.
- vendor_id for tenant isolation.
- vendor_members for employee/member access.
- RLS for security enforcement.
- Sharp for automatic image normalization.
- PWA first for low-cost mobile access.
- Legal pages and vendor agreements before paid public launch.

The main risk is not coding difficulty.
The main risk is launching without trust, tenant isolation, support boundaries, legal clarity, and operational discipline.

Build the foundation first, test it repeatedly, then add features.
