CANTEEN/CAFE MANAGEMENT SAAS - MVP SCOPE
========================================

Purpose:
- Prevent overbuilding.
- Keep architect and implementation agents focused on the first useful vendor-ready product.

MVP Goal:
- One real Pune vendor can safely run daily canteen/cafe operations from a phone-first web app.

Primary success question:
- Can one vendor manage menu, orders, kitchen flow, and queue safely without cross-vendor data leakage?


1. MVP MUST INCLUDE
===================

Foundation:
- NextJS App Router.
- Vercel-ready deployment.
- Supabase Auth.
- Supabase PostgreSQL.
- Supabase RLS.
- Supabase Storage.
- Mobile-first PWA layout.

Tenant and access:
- vendors table.
- profiles table.
- vendor_members table.
- vendor_id tenant isolation.
- role-based route access.
- active/disabled membership status.

Dashboards:
- Order dashboard.
- Kitchen dashboard.
- Queue dashboard.
- Control/admin dashboard.

Core operations:
- Menu category management.
- Menu item management.
- Item availability toggle.
- Order creation.
- Counter payment confirmation.
- Order status progression.
- Live queue display.

Storage:
- Vendor logo upload.
- Menu item image upload.
- Staff avatar upload.
- Image normalization using Sharp.
- media_assets metadata table.

Trust basics:
- Terms page.
- Privacy page.
- Support contact.
- Basic vendor settings.
- Basic audit logging for sensitive actions.

Testing:
- RLS tenant isolation tests.
- Role access tests.
- Manual mobile workflow tests.
- Manual order lifecycle test.
- Manual image upload test.


2. MVP SHOULD INCLUDE IF TIME ALLOWS
====================================

Useful but not blocking:
- Basic data export.
- Basic expense entry.
- Basic daily sales summary.
- Basic vendor onboarding checklist.
- Basic reconnect/stale-state banner for realtime.
- Basic staff invite flow.


3. DEFER UNTIL AFTER PILOT
==========================

Features to defer:
- Full khatabook system.
- Full profit/loss reports.
- Inventory stocking suggestions.
- Advanced stock recipe calculations.
- Customer login.
- Phone OTP login.
- Play Store release.
- Capacitor packaging.
- Subscription billing automation.
- Vendor self-service plan upgrades.
- Multi-branch vendor setup.
- Advanced analytics.
- Public marketplace behavior.
- Food delivery/payment settlement.


4. OUT OF SCOPE UNLESS EXPLICITLY APPROVED
==========================================

Do not build:
- Ads.
- Hidden monetization.
- Food marketplace features.
- Payment settlement to vendors.
- Customer wallet.
- Lending or credit scoring.
- Debt recovery automation.
- Data resale or vendor/customer profiling.
- Service role usage in browser.
- Cross-vendor reporting in vendor dashboards.


5. MVP RELEASE GATES
====================

Security gate:
- RLS enabled.
- Cross-vendor reads fail.
- Cross-vendor writes fail.
- Disabled member access fails.
- Role access matrix enforced.

Operations gate:
- Menu works.
- Orders work.
- Kitchen flow works.
- Queue updates work.
- Mobile layout works.

Trust gate:
- Terms page exists.
- Privacy page exists.
- Support contact exists.
- Admin access policy is documented.
- Pilot vendor understands the app is B2B software, not a food marketplace.

Pilot gate:
- One test vendor can be onboarded.
- One full order lifecycle can be completed.
- Basic data can be inspected/exported if needed.
- Known limitations are documented.


6. MVP AGENT RULES
==================

Agents should:
- Build only what supports the MVP goal.
- Ask before adding deferred features.
- Keep schema changes minimal and documented.
- Add RLS/security notes for every tenant-owned table.
- Prioritize role security over UI polish.

Agents should not:
- Start inventory suggestions before core order data is stable.
- Build reports before source data is reliable.
- Add Play Store work before PWA is validated.
- Add billing automation before legal/tax decisions are made.
- Expand scope because a feature seems useful.
